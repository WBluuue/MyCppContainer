4. Engineering standards
- Prefer simple C++20 designs and explain deliberate deviations from std::vector semantics.
- Maintain explicit invariants: typically 0 <= size_ <= capacity_; distinguish allocated raw storage from constructed T objects; only destroy objects whose lifetimes have begun.
- Respect alignment, allocation/deallocation pairing, RAII, nontrivial types, exception safety, and the danger of implicit shallow copies for owning pointers.
- For container raw-storage allocation, prefer std::allocator<T>/`std::allocator_traits` initially unless explicitly instructed otherwise; avoid new T[n] as a substitute for raw uninitialized capacity.
- For single-object UniquePtr ownership, adopt an already constructed object and pair scalar new with scalar delete under the default deletion policy. Do not allocate/copy T while adopting or observing it. Owned pointers have one deleting owner; get and dereference only borrow access. Arrays and incompatible allocation/deletion pairs are outside the current contract.
- Never silently use memcpy or memmove to relocate arbitrary T. Discuss appropriate move/copy semantics and exception guarantees when that milestone arrives.
- For performance work, benchmark in a suitable optimized build; describe environment and methodology; avoid invented performance numbers.
- Keep CMake target-based. Reuse Catch2/CTest, and preserve existing smoke tests. Favor targeted boundary tests, non-default-constructible and throwing/nontrivial types when relevant.
- Do not expand into DPDK, RDMA, threading, networking, lock-free, or other advanced components during the initial Vector phase.

U3 contract and preparation:
- Single goal: explicit control of deletion responsibility through `T* release() noexcept`, `void reset(T* ptr = nullptr) noexcept`, and `void swap(UniquePtr& other) noexcept`. These are non-const member operations. Nonmember/ADL swap, custom deleters, factories, arrays, fancy pointers, and converting ownership transfers are not part of U3.
- release returns the original stored pointer and clears the owner without deleting, constructing, or moving T. Empty/repeated release returns nullptr. The caller becomes responsible for deletion or immediate adoption by another owner; the original owner must never delete the released object.
- reset adopts nullptr or a new, independently adoptable scalar-delete-compatible pointer and releases the previous object exactly once. It must publish the new stored pointer before invoking the old T's destructor, so an old object's destructor observing owner.get() sees the replacement/null. The UniquePtr itself stays alive. reset() and reset(nullptr) clear ownership; repeated empty reset is harmless. Nonthrowing T destruction remains a precondition.
- A non-null reset argument must not equal the pointer currently owned by that same object or belong to another deleting owner. Thus nonempty `p.reset(p.get())` is outside the contract; no self-reset protection is required or tested. `p.reset(p.release())` is valid because argument evaluation empties p before reset executes; it must preserve the existing T without destruction.
- Member swap exchanges stored pointers, including all empty/owning combinations, without allocating or constructing/copying/moving/destroying T. Self-swap preserves state. Borrowed pointers to the objects remain valid; deletion responsibility changes owners. No public free swap overload is required.
- Eight new cases cover repeatable empty release; release with ownership handed to a standard-library cleanup guard and the old owner destroyed first; default/null/repeated reset; reset adoption/replacement with separate lifetime counts; old-destructor observation of reset's new pointer; release followed by re-adoption; four swap state combinations and swap-back; and empty/nonempty self-swap. The observer only reads get during T destruction and does not reenter mutating operations.
